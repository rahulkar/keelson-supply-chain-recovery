## 1. Engine canonical store + sync (Tier B/C)
Migration (engine): `scn_snapshot(id uuid, tenant, connector, source_snapshot_id, as_of, watermark, status {loading, ready, failed, superseded}, row_counts jsonb, bytes, duration_ms, error, created_at, ready_at)`, `scn_current(tenant, connector, snapshot_id, updated_at)` (pointer), `scn_pin(tenant, snapshot_id, plan_id)` (snapshots pinned by open plans are never GC'd), and one table per scn/1.0 entity `scn_<entity>` with the 25-scn-1.0 columns + `tenant`, `snapshot_id` (PK includes snapshot_id + source_id); all **RLS FORCE** like other tenant tables; indexes on (tenant, snapshot_id, …natural keys).
`core/scn_sync.py` (platform side): `async def sync_connector(tenant, connector, *, reason) -> SnapshotRow`:
1. reader principal FastMCP client via the egress proxy → `scn.snapshot_open(all entities)`;
2. for each entity `scn.snapshot_export` → download each part URL **through the egress proxy** (signed `http://merxa.localhost/v1/snapshots/…` URLs; refuse any other host unless it equals the connector host), stream to a temp file, verify sha256 + rows;
3. load with `COPY` into the `scn_*` tables under a new snapshot_id (status loading), check row counts against the manifest + FK sanity (every po_line.sku exists, every inventory location exists);
4. one transaction: mark previous ready snapshot `superseded`, set `scn_current` → new id, status ready; 5. GC: delete superseded snapshots older than the last 2 unless pinned.
Concurrency: one sync per (tenant, connector) at a time (advisory lock or lease row); idempotent; failures leave the previous snapshot current. Triggers: worker startup (after the tool snapshot), webhook events (debounced 30 s; any `change_set.*`, `po_line.*`, `inventory.*`, `sailing.*`), tier C poll every 5 min via `scn.changes_since(watermark)` (any change → full resync in M3), and `POST /api/admin/connectors/{slug}/sync` (tenant-admin) + `GET /api/admin/connectors/{slug}/snapshots` (status, counts, durations). **The case path never waits for a sync.** Target (spike S5): full-profile sync < 60 s, ≤ 600 MB peak RSS in engine-worker.

## 2. ProblemData v2 (contracts-py `keelson_contracts.optimizer`, all new fields optional)
Added to `ProblemData`:
- `locations: [{code, kind: dc|cluster|store|factory|supplier|port, name, lat_e6:int, lon_e6:int, parent}]` (map only; degrees × 1e6 as int)
- `po_lines: [{ref "<po>#<line>", po_code, supplier_code, factory_code, dest_dc, sku, qty, eta, ex_factory, mode: sea|sea_air|air|road, lane_code}]` (receipts remain the canonical arrival list; po_lines give provenance for levers)
- `bom: [{style_code, component_code, supplier_code, factory_code|null}]`
- `inbound_lanes: [{code, origin, dest_dc, mode, transit_days, cost_per_unit_cents, weekly_capacity_units, via: [str]}]` (sea-air etc.; per-unit cost derived from rate card)
- `alt_sources: [{supplier_code, factory_code, style_codes:[str], lead_time_days, unit_cost_cents, moq_units, weekly_capacity_units, approved: bool, compliance_ok: bool, lane_code}]`
- `production: [{line_code, factory_code, daily_capacity_units, orders:[{code, po_line_ref, sku, qty, planned_start, planned_end, seq}]}]`
- `allocations: [{code, sku, dc_code, cluster_code, ship_week, qty, protected: bool, version}]` (cluster-aggregated view keeps the Merxa allocation codes for actions)
Perturbation targets extended: `kinds` may be `supplier|component|factory|port|chokepoint|lane|po_line|receipt|cluster|dc|style`. Resolution rules (deterministic, in the optimizer): `lead_time_shift` on supplier/component → every po_line whose style's BOM uses that supplier/component at that factory; on factory → its po_lines; `capacity_scale` on port/chokepoint → inbound lanes whose `via`/origin/dest includes it (capacity 0 ⇒ lane unusable ⇒ its receipts shift by `alt_lane` extra days if provided in `via` metadata, else lost); `demand_scale` as before.

## 3. Optimizer v2 endpoints
- `POST /v1/impact` gains `include_graph: bool = false` and returns (when true) `graph: {nodes:[{id, kind, label, status: disrupted|impacted|at_risk|ok, units_at_risk, first_breach_week|null}], edges:[{source, target, kind: supplies|produces|ships|stocks|serves}]}` grouped to stay ≤ 300 nodes (group stores to clusters, po_lines to POs, skus to styles) and `tts: [{dc_code, cluster_code|null, tts_days, ttr_days|null, verdict: ok|expedite|loss}]` (Simchi-Levi TTS LP per DC with the perturbed receipts; TTR from the perturbation window; verdict TTR<TTS → ok, ≈ → expedite, > → loss) + `bottlenecks: [{name, shadow_price_cents}]`.
- `POST /v1/optimize` accepts `plan_spec.levers` from the v1 lever set (any combination) composed into ONE model per request:
  | lever | model effect | actions (Merxa ops) |
  |---|---|---|
  | `reallocate_inventory` | as M1 | `transfer_order.create` |
  | `expedite_mode_shift` | move qty of affected po_lines to a `sea_air`/`air` inbound lane (weekly capacity × capacity_scale; premium cost) → earlier arrival | `po_line.split {mode, qty, lane_code}` + `capacity_booking.create {lane_code, iso_week, qty_units}` |
  | `resource_alt_supplier` | buy from an approved & compliant alt source (lead time, MOQ via CP-SAT or LP + MOQ repair, capacity, unit-cost premium); the original po_line qty is reduced by the same qty | ONE atomic group: `po.create {supplier_code, factory_code, dest_dc, eta_dc, lines}` + `po_line.change_qty` (or `po_line.cancel` when reduced to 0) |
  | `prioritize_allocation` | re-split scarce DC stock across clusters by grade/protected minimums to minimise lost margin | `allocation.set_qty` (expected_version from allocations[].version) |
  | `resequence_production` | within a factory line, reorder orders so styles whose trims are available / peak-critical are produced first (deterministic CP-SAT with `num_workers=1` or exact small enumeration; document) → changes receipt dates of affected po_lines | `production_order.resequence {line_code, order_codes}` + `po_line.reschedule` for changed ETAs |
  Response adds: `scorecard {fill_rate_bp, lost_units, lost_margin_cents, incremental_cost_cents, cost_breakdown:{transfer, expedite_premium, nearshore_premium}, net_benefit_cents, shortage_days, first_breach_shift_days, tts_gain_days, changes}`, `decisions` per lever, and `actions` ordered deterministically (groups that must be atomic carry the same `group` id). KPIs always recomputed from the rounded plan; fallback to do-nothing if no improvement (as M1).
- `GET /v1/levers` lists the five levers with `params_schema` and required `ops`.
- **S4**: full profile (180 SKUs × 18 clusters × 9 weeks, all levers) solves in < 5 s at concurrency 1 inside the 512 MB container; record timings.

## 4. Engine workflow (M3)
- `frame_case`/`quick_exposure`/`impact` build ProblemData **from the current scn snapshot** (`runtime/problem_scn.py`, SQL aggregates to cluster level; fall back to the M2 MCP gatherer, labelled advisory, when the connector has no snapshot). Plans pin their snapshot (`scn_pin`).
- `simulate` runs deterministic **candidate plans** from the tenant's enabled levers (AgentSpec `planning.candidates`, default):
  A "Rebalance between DCs" [reallocate_inventory] · B "Rebalance + targeted sea-air" [reallocate_inventory, expedite_mode_shift] · C "Near-shore top-up + resequence" [resource_alt_supplier, resequence_production] · D "Hybrid" [all enabled levers] · plus "Do nothing". **Capability check**: an option whose levers need ops the connector cannot apply (tool not approved / op unsupported) is marked `guided_only` (still simulated; Apply disabled with reason; Guide is M5). CI test: every enabled lever's ops ⊆ Merxa's supported ops.
- `compose` emits (inline ≤ 2): `kpi_strip`, `recommended_option`; canvas: `scenario_compare`, `network_map`, `impact_graph`, `stockout_timeline`, `plan_diff`, `evidence_pack`.
- `compile_changeset` maps all v1 ops (identity mapping for Merxa); atomic groups stay in one change set. Policy: expedite / near-shore / resequence ops always require human approval (Merxa auto caps only allow transfer/allocation anyway).

## 5. New render blocks (contracts-py `blocks.py`; JSON Schema → Zod)
Large payloads go in `data_ref` (`/api/blocks/{id}/data`); props carry a summary.
- `network_map@1` — props `{title, summary:{nodes, at_risk_nodes, lanes}, bbox:[w,s,e,n] (e6 ints), legend:[…]}`; data `{nodes:[{id, kind, label, lat_e6, lon_e6, status, units_at_risk|null}], links:[{id, kind: inbound|transfer|sea_air|nearshore, from, to, path:[[lon_e6,lat_e6]…], status, units|null, option_id|null}], footprint: GeoJSON|null}`. Sea paths come from `data/geo/sea_routes.json` (hand-made waypoints for Chittagong/Colombo/HCMC/Jebel Ali → Felixstowe/Rotterdam/Hamburg/Gdańsk via Cape or Suez, Tanger Med, Istanbul; road lanes straight).
- `impact_graph@1` — props `{summary:{nodes, disrupted, impacted}}`; data `{nodes:[{id, kind, label, status, units_at_risk, first_breach_week}], edges:[{source,target,kind}]}` (≤ 300 nodes).
- `stockout_timeline@1` — props `{weeks:[IsoWeek], options:[{id,title}]}`; data `{rows:[{id, dc_code, cluster_code, style_code, label, cells:[{week, status: ok|tight|short, shortage_units}], first_breach_week|null, by_option:{<option_id>: first_breach_week|null}}]}` (top 40 rows by shortage).
- `scenario_compare@1` — props `{options:[{id, title, levers:[str], scorecard:{…as §3…}, recommended: bool, guided_only: bool, guided_reason|null, pareto: bool}], axes:{x:"incremental_cost_cents", y:"lost_units"}}`.
